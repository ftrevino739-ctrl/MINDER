# MINDER — Project plan

## Product direction

MINDER is a personal desktop assistant for Windows first, with cross-platform support retained where practical. It should feel like a polished, responsive desktop product—not a demo.

In plain terms, this is the user's Jarvis-style computer assistant—not an OS or a browser. It combines voice and text conversation, a user-selected reasoning provider, speech recognition and synthesis, safe desktop/browser/file/coding tools, persistent inspectable memory, and a Liquid Glass-inspired HUD. Product-facing identity is MINDER; legacy Jarvis class names are internal compatibility details. The wake-word work is only an optional local hands-free entry path into this assistant; it must never replace the conversation engine, automate microphone startup, or turn MINDER into a single-purpose wake-word project. Push-to-Talk and text input remain first-class paths.

The starting codebase is Mark LVI by FatihMakes. This repository is an independent rebrand/adaptation, not a fork. The upstream attribution and CC BY-NC 4.0 terms remain in place. Read LICENSE before redistributing or using the project commercially.

## Product requirements

- Voice-first interaction with a reliable text fallback.
- Understand requests, plan multi-step work, and use desktop tools.
- Open applications, navigate supported interfaces, write code, and manage files.
- Persistent, inspectable memory with user control.
- Confirm destructive or irreversible actions before execution.
- Clear status, progress, errors, and truthful reporting—never claim an action succeeded unless verified.
- A polished MINDER identity and a premium, restrained Liquid Glass-inspired interface.
- Provider choice belongs to the user. Do not silently change providers or send audio/screen data to a different vendor.

## Hardware and model strategy

Target development machine: Windows 11 with 8 GB RAM.

- Do not require a large local language model. Prefer hosted inference for the main reasoning model until benchmarks prove a local option fits comfortably.
- Keep local speech-to-text and text-to-speech options available where they are practical on CPU.
- Make provider credentials opt-in and store them locally; never commit secrets.
- Gemini Live is optional, not the default. An unconfigured or failed provider must not silently fall back to Gemini.
- Select exact providers, model IDs, free-tier limits, and voice after current verification and a measured comparison. Do not hard-code unverified free-tier claims.

## Implementation phases

1. **Foundation — completed:** import the source independently, preserve attribution/license, establish CI, and apply MINDER identity to core defaults and desktop integration.
2. **Provider setup — foundation in place; provider selection pending:** the provider pipeline is the default, first-run no longer needs a Gemini key, existing config is preserved, and both conversation turns and one-shot helpers stay on the selected LLM without silently falling back to Gemini. Coding jobs use the explicit CODING provider or the active pipeline LLM. Provider probes and model/voice discovery run in background workers. Automatic discovery and manual refresh share a per-provider generation gate; stale responses are discarded, selection-only changes do not invalidate the catalogue, and SHA-256 fingerprints do not expose credentials. Concurrent builds of the same STT/TTS model are coalesced. A real endpoint/model/voice combination and measured latency still need to be selected.
3. **Voice experience — in progress:** microphone device selection and the audio settings tests are in place. The provider regression now drives synthetic PCM through automatic VAD → STT → LLM → TTS and separately checks PTT buffering until release. The desktop audio queue places the PTT release flush after all accepted microphone frames, rejects late frames, reserves a control slot for a release barrier under queue saturation so next-turn PCM cannot overtake it, and reports dropped-frame backpressure safely. Real microphone/speaker tests, latency tuning, voice selection, automatic barge-in and Windows hardware acceptance remain pending. Keep the pretrained “Hey Jarvis” detector disabled until a genuine MINDER wake-word model exists.
4. **Desktop actions — automated safety pass in place; Windows acceptance pending:** browser, desktop input, file copy/move/rename/delete, app launching, reminders, reports, Steam/Epic updates and human-approved messaging have focused regression coverage. Dangerous Windows URI schemes are blocked. Plugin modules are statically inspected and remain off until the user approves the exact SHA-256 source. The actual app, UI, native dialogs, accounts, voice devices and end-to-end workflows still require Windows acceptance.
5. **Interface — in progress:** applied the MINDER midnight-slate palette and frosted-glass treatment to onboarding and ENGINE & PROVIDERS, then extended translucent surfaces, soft shadows and rounded corners across the transcript, header/footer, side-monitor frame, customization, camera preview, plugin manager/settings, clipboard, confirmation, audio-device, memory and remote-access overlays. The Windows Qt smoke test checks the transcript, four frame surfaces and the floating panels with safe fixtures. The Qt smoke test now checks the minimum supported and default window sizes for sidebar overlap and centre-HUD space. Remaining work is detail-level visual polish, broader display-scale/DPI review and hardware/display acceptance on the target PC.
6. **Reliability and release — in progress:** expand automated tests, error recovery and logging; then validate, package, and document a repeatable Windows installation path.

- **Core voice interruption improvement (2026-11-21):** audited the actual `main.py` UI interrupt path into `PipelineEngine`. The local pipeline's old `interrupt()` called `asyncio.Task.cancel()` directly even though the UI can invoke it from the Qt/hotkey thread, and it never emitted the Live-shaped `turn_complete` event on cancellation. That could leave MINDER in its interrupted state and cause later microphone frames to be discarded. The engine now binds its owning asyncio loop, marshals cancellation with `call_soon_threadsafe` from foreign threads, cancels current TTS/LLM generation on the event loop, clears queued follow-up injections, and emits one terminal event so the existing main.py receive loop can resume listening. Regression tests cover interruption from a worker/UI thread, interruption from the owning loop, the completion event, TTS cancellation, a safe no-loop no-op, preservation of normal tool follow-up, and suppression of late tool results from an interrupted turn (without blocking a newer user request). CI run [44920575295](https://github.com/ftrevino739-ctrl/MINDER/actions/runs/44920575295) passed all five jobs; Windows regression ran 312 tests with one platform-specific skip, and provider regression passed. This is explicit user-triggered interruption only: `barge_in` remains false because automatic detection of a user speaking over MINDER has not been implemented. It does not forcibly cancel an already-dispatched desktop action/tool operation, but records its eventual result without automatically restarting the interrupted spoken answer. The user's full assistant vision remains the priority; wake word stays optional/off by default.
- **Tool-dispatch interruption hardening (2026-11-21):** `main.py` now routes multi-call model batches through `core/tool_dispatch.py`. The cross-thread interrupt flag is protected by a shared lock, calls not yet admitted when interruption arrives receive explicit not-executed responses, and a captured-but-not-yet-injected vision image is discarded rather than silently becoming a new turn. Operations already admitted or underway are not forcibly cancelled. Regression tests cover ordered calls, pre-interrupted batches, interruption during the first call, UI-thread signalling, and a mixed batch containing an already-dispatched action plus skipped calls.
- **PTT release ordering under backpressure (2026-11-21):** a full bounded microphone queue could let the async flush-marker waiter be overtaken by a newly scheduled frame in a narrow scheduling race. `core/ptt_queue.py` now uses `MicrophoneQueue`, which reserves one temporary control slot for the release marker while keeping the PCM capacity bounded; `main.py` uses it for each session. Five focused tests cover held-key gating, normal FIFO turn boundaries, barrier survival when full, the former overtaking race, and overflow reporting. Four focused tool-dispatch tests were also run locally; both isolated suites passed in the local harness. The full GitHub Actions result for these newest commits has not yet been verified, so this is not a release or hardware-acceptance claim.
- Wake-word training compatibility audit (2026-11-17): the upstream `openwakeword/train.py` path is not approved for native Windows 11 yet. Its current DataLoader multiprocessing and full false-positive window materialization are Windows/RAM risks on the 8 GB target PC. The official `[full]` extra contains legacy TensorFlow/ONNX-TF and TorchAudio constraints that should not be installed blindly for an ONNX-only workflow. The dscripka Piper fork does require `webrtcvad` and `espeak_phonemizer`; these remain in the preflight dependency checks. A community Windows-native orchestration is a candidate only, not an approved dependency; it needs pinned-source, licensing, data-hash, bounded-memory and output-compatibility review. See [MINDER_WAKE_WORD_WINDOWS_COMPATIBILITY.md](MINDER_WAKE_WORD_WINDOWS_COMPATIBILITY.md). No training assets have been downloaded and no training has started.
- The provider regression runner emits a non-fatal warning that multimedia playback is unavailable in the headless Linux CI environment; real audio/video devices are not tested there. Wake-word detector lifecycle has been hardened: each run owns an isolated queue, stop event and model; disabling wake word stops the worker; model-load failures leave the preference disabled. The bundled model still detects the legacy phrase “Hey Jarvis”; keep it disabled until a genuine MINDER model is provided. Its optional `--verify-imports` mode actually imports the training modules to catch binary/DLL failures and rejects mismatched PyTorch/TorchAudio version or build tags; the default remains a lighter module-discovery check. ## Working rules

- Make small, reviewable commits.
- Inspect the existing implementation before changing behavior.
- Run syntax checks and focused tests after each change; run the app on Windows before calling a feature complete.
- Back up user configuration before migrations.
- Never commit API keys, tokens, memory databases, recordings, or personal data.
- Keep a change log of behavior changes and known limitations.
